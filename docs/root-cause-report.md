# BigKinds 장시간 정지 및 브라우저 종료 원인 판정 보고서

## 판정 요약

2026-07-30 장시간 정지의 **최초 외부 촉발 요인**은 기존 기록만으로 확정할 수 없다. 해당 실행은 1단계 관측 필드가 적용되기 전이어서 정지 중 하트비트, worker 종료 코드, 브라우저 연결 종료 이벤트와 취소 요청 출처가 남지 않았다.

다만 기존 기록, 1단계 관측 자료와 격리된 장애 주입으로 다음 구조적 원인은 확정했다.

1. 개별 Playwright 이동에는 timeout이 있지만 기사 한 건의 클릭·이동·판정·검증·정리 전체에는 상위 deadline이 없다.
2. 기사 작업과 취소 신호를 동시에 기다리지 않으므로 기사 작업이 반환하지 않으면 하트비트만 갱신되고 진행과 취소 처리는 멈춘다.
3. 검사 페이지, Chromium과 Playwright 드라이버 종료는 첫 실패 호출에서 같은 `Target page, context or browser has been closed` 오류로 나타날 수 있다. 현재 수집기는 브라우저 연결 종료를 별도 기록하거나 세션을 재생성하지 않는다.
4. 이슈 내부 예외가 발생해도 `_audit_region()`이 성공을 반환할 수 있고, 체크포인트의 `issue` 레코드는 완료가 아닌 시작을 뜻한다. 따라서 미완료 이슈 또는 지역이 완료로 기록될 수 있다.
5. worker 비정상 종료는 PID와 종료 코드로 판정되지만 watcher가 `current_operation`을 지운다. 브라우저 비정상 종료도 `finally`에서 최종적으로 `stopped`를 기록하므로 마지막 장애 계층을 종료 후 상태만으로 구분할 수 없다.
6. API 정상 종료는 worker에 취소를 요청한 뒤 1초만 기다리고 프로세스 추적 목록을 비운다. 유예시간 안에 끝나지 않은 worker를 종료하거나 계속 감시하는 폴백이 없다.

따라서 후속 구현의 우선순위는 기사 상위 deadline과 취소 폴백, 체크포인트 완료 의미 수정, 브라우저 연결 종료 관측과 제한된 세션 복구 순이다. worker 자동 재시작, API 서버와 실행기 분리, 서버 시작 시 자동 재개는 이번 원인에 대한 직접 증거가 없어 범위에서 제외한다.

## 조사 범위와 제약

- 시간은 모두 Asia/Seoul 기준이다.
- 운영 자료는 `work/`의 SQLite, 감사 로그와 서버 로그를 읽기 전용으로 분석했다.
- 장애 주입은 `tests/test_fault_injection.py`가 생성하는 임시 SQLite와 자식 프로세스에서만 수행했다.
- Windows 절전·로그오프는 현재 실행 세션을 중단시키고 결과 보존을 보장할 수 없어 수행하지 않았다.
- 2026-07-30 실행은 상세 관측 기능 적용 전이므로 최초 브라우저 종료 시각과 종료 주체는 추론하지 않는다.

## 분리 장애 주입 결과

### 느린 HTTP 응답

로컬 서버가 1초 동안 응답하지 않게 하고 `BrowserLinkChecker` timeout을 150ms로 설정했다. 검사는 1.5초 이내에 `타임아웃` 판정으로 반환됐다.

판정: 일반 `page.goto()` 응답 지연은 기존 호출 단위 timeout으로 제한된다. 50분 공백은 단일 HTTP 이동 timeout만으로 재현되지 않는다. 기사 전체 흐름, 이벤트 대기 또는 정리 호출을 감싸는 상위 deadline 부재가 남는다.

### 반환하지 않는 기사 연산

`current_operation=link_check:2026-07-30:부산광역시:issue_5:source_8` 상태를 유지한 채 하트비트 루프를 실행했다.

| 상대 시각 | heartbeat | last progress | 상태 |
| --- | --- | --- | --- |
| 0초 | worker 시작 시각 | 없음 | `running` |
| 약 5초 | 갱신됨 | 없음 | `running` |
| 취소 요청 직후 | 갱신됨 | 없음 | `cancel_requested` |

마지막 연산은 유지되지만 종료 시각은 생기지 않았다. 현재 취소 토큰은 기사 사이에서만 확인되므로, 하트비트가 정상이라는 사실이 실제 진행 또는 취소 가능성을 뜻하지 않는다.

### 검사 페이지, Chromium, Playwright 드라이버 종료

세 계층을 각각 닫은 뒤 첫 `page.title()` 호출을 실행했다. 세 경우 모두 이 환경의 Playwright에서 `Target page, context or browser has been closed` 계열 오류가 관측됐다.

판정: 오류 문자열만으로 종료 계층을 확정할 수 없다. `page.on("close")`, `browser.on("disconnected")`와 Playwright 수명주기 이벤트를 같은 타임라인에 기록하고, 브라우저 연결 여부로 페이지 단독 종료와 세션 종료를 구분해야 한다.

### worker 강제 종료

별도 worker가 기사 연산을 기록하고 결과 1건을 저장한 뒤 `os._exit(23)`으로 종료됐다.

| 항목 | 관측값 |
| --- | --- |
| worker PID | 자식 프로세스 PID와 일치 |
| 종료 코드 | `23` |
| 종료 상태 / 사유 | `partial_failed` / `worker_exited_unexpectedly` |
| 하트비트 | 기록됨 |
| 마지막 진행 | 없음 |
| 브라우저 상태 | `running` |
| 마지막 연산 | watcher 처리 후 빈 문자열 |

PID·종료 코드 기반 판정은 동작한다. 그러나 비정상 종료 시 마지막 연산과 시작 시각을 지우면 어느 기사에서 종료됐는지 사후 판정할 수 없으므로 보존해야 한다.

### API 정상 종료와 비정상 종료

API lifespan을 별도 프로세스에서 실행했다.

- 정상 종료: 같은 PID로 `started` → `stopping` → `stopped`, 종료 코드 0.
- 프로세스 강제 종료: `started`만 남고 `stopping`·`stopped`가 없으며 종료 코드가 0이 아님.

강제 종료된 프로세스 내부에서 종료 이유를 추가로 기록하는 것은 불가능하다. 다음 시작 이벤트와 직전 `stopped` 부재를 조합해 비정상 종료로 판정해야 한다. 서버 분리나 자동 작업 재개가 필요하다는 증거는 이번 장애에서 확인되지 않았다.

별도 특성화 실행에서 서버 종료는 활성 worker에 `cancel_requested_by=server_shutdown`을 기록하고 1초를 기다렸지만, worker가 계속 살아 있어도 추적 목록을 비웠다. 이 동작은 취소 유예시간과 강제 종료 폴백으로 보완해야 한다.

### 화면 중단 요청

API를 통해 기사 연산 중인 작업에 취소를 요청했다. `cancel_requested_at`과 `cancel_requested_by=user`는 즉시 기록됐지만 `current_operation`은 유지되고 `ended_at`은 비어 있었다.

판정: UI와 API의 요청 전달은 정상이다. 지연 원인은 프런트엔드가 아니라 worker가 기사 작업 중 취소 토큰을 동시에 기다리지 않는 실행 구조다.

### Windows 절전 후 복귀

실행하지 않았다. 2026-07-30 당시 절전·로그오프·수동 Chromium 종료 여부를 확인할 Windows 이벤트 자료도 저장소에 없다. 이 항목은 최초 외부 촉발 요인의 미확정 후보로만 유지하고 자동 재개 구현의 근거로 사용하지 않는다.

## 후속 구현 결정

1. 기사 상위 deadline은 `min(180, max(45, timeout_seconds * (retries + 1) + 15))`초로 계산한다. 현재 기본값 30초·재시도 2회에서는 105초다.
2. 취소 토큰은 최대 0.5초 간격으로 기사 작업과 동시에 기다린다.
3. 취소 요청 후 10초 동안 협력 종료를 기다리고, 끝나지 않으면 기록된 worker PID를 종료한다. 종료 후 5초 안에 끝나지 않는 경우에만 동일 PID에 최종 종료를 적용한다.
4. 페이지·컨텍스트·브라우저 정리는 각 5초, 전체 10초를 넘기지 않는다.
5. 비정상 브라우저 연결 종료는 기사당 1회, 작업당 2회까지만 세션을 재생성한다. 상한을 넘으면 `partial_failed` 또는 `failed`로 종료한다.
6. 자동 worker 재시작, 서버 시작 시 자동 재개, API 서버와 작업 실행기 분리는 구현하지 않는다.
7. 사용자 취소 작업은 어떤 경우에도 자동 재개하지 않는다.
8. 체크포인트에 이슈 `started`·`completed`·`failed`를 구분한 뒤 브라우저 복구를 활성화한다.

세부 단계와 대상 파일은 `docs/implementation-plan.md`의 3~8단계에 반영한다.

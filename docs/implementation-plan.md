# BigKinds 지역 이슈 링크 점검 안정화 구현 계획

## 목표

이 계획의 목표는 다음 세 가지다.

1. 지정한 날짜와 지역의 이슈 및 기사 링크 점검이 특정 기사, Playwright 브라우저, 작업 프로세스 또는 API 서버의 장애 때문에 설명 없이 멈추지 않도록 한다.
2. 진행 화면에 다음 세 범위의 진행률을 함께 표시한다.
   - 전체 일정: 완료된 날짜×지역 수 / 전체 날짜×지역 수
   - 현재 지역 이슈: 완료된 이슈 수 / 현재 날짜·지역의 전체 이슈 수
   - 현재 이슈 기사: 처리 완료된 기사 수 / 현재 이슈의 전체 기사 수
3. 사용자가 화면에서 중단을 요청하면 정해진 시간 안에 작업이 종료되고, 완료된 체크포인트와 가능한 부분 결과가 보존되도록 한다.

이 문서의 핵심 원칙은 **종료 원인을 먼저 관측하고 재현한 뒤, 그 결과에 맞게 해결 단계와 변경 범위를 수정하는 것**이다. 관측 전에 브라우저 복구, 작업 프로세스 재시작 또는 서버 분리 중 하나를 최종 해결책으로 확정하지 않는다.

## 현재 구조

### 실행 및 데이터 흐름

1. `frontend/src/App.tsx`가 날짜·지역·실행 옵션을 입력받아 `POST /api/jobs`를 호출한다.
2. `src/api/routes_jobs.py`가 요청을 `JobManager`에 전달한다.
3. `src/application/job_manager.py`가 작업을 SQLite에 저장하고 Windows `spawn` 방식의 별도 작업 프로세스를 시작한다.
4. 작업 프로세스는 `AuditService`를 통해 `RegionalCollector`를 실행한다.
5. `RegionalCollector`는 Playwright로 날짜 → 지역 → 이슈 → 출처 기사 순서로 점검한다.
6. 기사 한 건이 끝날 때마다 `CheckpointStore`가 JSONL 체크포인트에 결과를 추가하고, 진행 이벤트가 SQLite에 반영된다.
7. 날짜×지역 단위가 끝나면 해당 단위를 완료 처리한다.
8. 실행 종료 후 누적 체크포인트로 Excel을 생성하고 결과 요약을 SQLite에 저장한다.
9. 프런트엔드는 1.5초마다 작업 상태와 최근 로그를 조회한다.

### 현재 진행률

현재 전체 진행률은 `completed_regions / total_region_units`로만 계산된다. 여기서 단위는 날짜×지역이다. `issue_started`, `links_discovered`, `link_completed` 이벤트는 이미 존재하지만 전체 진행률 계산에는 사용되지 않는다.

### 현재 중단 처리

화면의 중단 버튼은 SQLite 작업 상태를 `cancel_requested`로 변경한다. 작업 프로세스는 날짜·지역·이슈·기사 사이의 `_raise_if_cancelled()` 호출 지점에서 이 상태를 확인한다. Playwright 호출이나 페이지 정리 과정이 멈추면 다음 확인 지점에 도달하지 못하므로 중단 요청이 장시간 적용되지 않을 수 있다.

### 현재 확인된 장애 증거

가장 최근 전체 지역 실행 기록에서는 서울·부산까지 128개 링크를 처리한 뒤 부산의 마지막 기사에서 약 50분간 진행이 없었다. 이후 여러 지역에서 `Target page, context or browser has been closed` 또는 드라이버 연결 종료 오류가 발생했고 작업은 `cancelled`로 끝났다.

확인된 문제는 다음과 같다.

- 브라우저 또는 컨텍스트가 닫힌 후 세션을 재생성하지 않는다.
- 기사 한 건 전체를 감싸는 상위 제한시간이 없다.
- 작업 생존 하트비트와 실제 진행 시각이 분리되어 기록되지 않는다.
- 작업 프로세스 PID·종료 코드와 서버 종료 원인이 남지 않는다.
- 이슈 처리 예외가 있어도 지역이 완료 체크포인트로 기록될 수 있다.
- 이슈 체크포인트는 완료 시점이 아니라 시작 시점에 기록된다.
- 서버 종료 시 실행 중인 작업에 취소 요청을 설정한다.

다만 최초 원인이 Playwright 호출 정지, Chromium 종료, 작업 프로세스 장애, API 서버 종료, Windows 절전 또는 외부 종료 중 무엇인지는 현재 자료로 확정할 수 없다.

## 채택한 방식과 이유

### 1. 진단 우선 방식

첫 번째 변경은 복구 로직이 아니라 관측 기능이다. 서버, 작업 프로세스, Playwright 브라우저 중 어느 계층이 먼저 멈추는지 확인할 수 있도록 로그·하트비트·PID·종료 코드를 남긴다.

이 방식을 채택하는 이유는 서로 다른 장애에 같은 복구 방법을 적용하면 다음 문제가 생길 수 있기 때문이다.

- 서버 종료가 원인인데 브라우저만 재생성하면 작업은 여전히 중단된다.
- 기사 호출 정지가 원인인데 작업 프로세스만 재시작하면 같은 기사에서 반복 정지할 수 있다.
- 사용자 중단과 비정상 종료를 구분하지 않으면 취소한 작업이 자동 재시작될 수 있다.
- 원인이 확인되지 않은 상태에서 별도 서비스로 분리하면 불필요하게 운영 복잡도가 커진다.

### 2. 원인 판정 게이트

관측 기능을 적용한 뒤 장애를 재현하고 `docs/root-cause-report.md`에 다음을 기록한다.

- 장애 발생 시각과 최초 이상 이벤트
- 서버·작업 프로세스·Playwright의 시간순 상태
- 마지막 정상 진행 단계와 정지한 연산
- 취소 요청 출처와 처리 시간
- 프로세스 종료 코드
- 확정 원인 또는 남은 후보

이 보고서가 작성되면 이 구현 계획의 후속 단계, 변경 파일 및 완료 기준을 실제 원인에 맞게 수정한다. **원인 판정과 계획 수정이 끝나기 전에는 자동 재시작, 서버 분리 등 근본 해결 구현을 시작하지 않는다.** 단, 관측 과정에서 안전을 위해 필요한 로그 보존과 테스트 전용 장애 주입만 허용한다.

### 3. 조건부 해결 방식

관측 결과에 따라 다음과 같이 해결책을 선택한다.

| 관측 결과 | 우선 해결 방식 |
| --- | --- |
| 하트비트는 갱신되지만 기사 진행이 정지 | 기사 전체 제한시간, 취소 가능한 비동기 작업, 정리 timeout |
| Chromium·컨텍스트가 먼저 종료 | 브라우저 세션 재생성, 현재 날짜·지역 복원, 미완료 기사 재개 |
| 작업 프로세스가 먼저 종료 | 종료 코드 기록, 제한 횟수 자동 재실행, 체크포인트 재개 |
| API 서버가 먼저 종료 | 종료 이유 보존, 시작 시 자동 복구 또는 작업 실행기 분리 |
| Windows 절전·로그오프가 원인 | 재개 시각 보정, 시작 시 자동 재개; 종료 중 지속 실행은 별도 운영 방식 검토 |
| 사용자 취소 후 정리 과정이 정지 | 협력적 취소 후 유예시간 기반 프로세스 종료 폴백 |

2단계 결과 기사 전체 정지와 브라우저 연결 소실 뒤 연쇄 실패는 재현됐고, worker·API 선행 종료와 Windows 절전은 원인으로 확정되지 않았다. 따라서 후자의 자동 재실행·서버 분리·절전 복구 항목은 후속 구현에서 제외한다.

### 4. 계층형 진행 UI

한 개의 진행 카드 안에 세 개의 막대를 세로로 배치한다.

```text
전체 일정                 2 / 17       12%
[████░░░░░░░░░░░░░░░░]

현재 지역 이슈             4 / 5        80%
[████████████████░░░░]

현재 이슈 기사             7 / 8        88%
[█████████████████░░░]
```

- 전체 일정은 기존 날짜×지역 기준을 유지한다.
- 이슈 진행률은 현재 날짜·지역 범위에서 계산한다.
- 기사 진행률은 현재 이슈 범위에서 계산한다.
- 아직 분모를 알 수 없으면 `이슈 목록 확인 중` 또는 `기사 목록 확인 중`으로 표시하고 임의의 0%를 표시하지 않는다.
- 전체 누적 `processed_links`는 별도 지표로 유지한다.
- 미래 지역의 이슈·기사 수를 얻기 위한 사전 순회는 하지 않는다. 이 방식은 정확도를 유지하면서 사이트 요청과 실행시간 증가를 피한다.

## 변경 대상 파일

2단계 원인 판정 후 범위를 다시 검토했다. 1단계에서 만든 저장소·worker·collector 구조는 유지한다.

### 2단계 산출물

- `docs/root-cause-report.md`: 운영 자료와 장애 주입 타임라인, 확정 원인과 미확정 후보
- `docs/implementation-plan.md`: 확정 원인에 맞춘 3~8단계와 timeout·재시작 정책
- `tests/test_fault_injection.py`: 느린 응답, 브라우저 계층 종료, worker·API 종료와 취소 요청 특성화

### 3~5단계 백엔드

- `src/application/job_repository.py`: 취소 단계, 비정상 종료 시 마지막 연산 보존, 종료 사유 저장
- `src/application/job_manager.py`: 취소 유예시간 감시와 기록된 worker PID 종료 폴백
- `src/application/audit_service.py`: 취소·부분 실패 후 체크포인트 기반 Excel 후처리
- `src/regional_collector.py`: 기사 상위 deadline, 동시 취소 대기, 정리 timeout, 브라우저 연결 종료 감지와 제한된 세션 복구
- `src/checkpoint.py`: 이슈 `started`·`completed`·`failed`와 이전 JSONL 호환
- `src/date_navigation.py`: 세션 복구 뒤 현재 날짜 복원 경계
- `src/api/routes_jobs.py`: 취소 API 멱등성과 취소 단계 반환

### 6단계 API 및 UI

- `src/application/job_repository.py`: 현재 이슈·기사 진행 분자와 분모 저장
- `src/api/routes_jobs.py`: 확장된 진행·취소 상태 반환
- `frontend/src/types.ts`: 이슈·기사 진행과 취소 단계 타입
- `frontend/src/App.tsx`: 3단계 진행 카드와 취소 상태 표시
- `frontend/src/styles.css`: 3개 막대의 데스크톱·모바일 레이아웃

### 테스트

- `tests/test_fault_injection.py`
- `tests/test_job_manager.py`
- `tests/test_audit_service.py`
- `tests/test_api_jobs.py`
- `tests/test_browser_link_flow.py`
- `tests/test_checkpoint.py` 신규 추가
- `frontend/src/App.test.tsx`

`run_web.py`, `src/api/app.py`, `src/logging_utils.py`, worker 자동 재시작과 API 실행기 분리는 1단계 관측 범위를 유지하며 후속 변경 대상에서 제외한다. 관련 회귀 테스트가 실패할 때만 다시 검토한다.

## 단계별 작업

### 0단계: 기준선 확보와 테스트 환경 복구

1. 현재 SQLite, 체크포인트 및 로그를 읽기 전용으로 보존한다.
2. 깨진 `.venv`를 대신할 재현 가능한 Python 테스트 환경을 준비한다.
3. 변경 전 전체 백엔드·프런트엔드 테스트 결과를 기록한다.
4. 기존 실패와 새 변경으로 인한 실패를 구분한다.

### 1단계: 종료 원인 관측 기능

1. 작업에 다음 필드를 추가한다.
   - `worker_pid`
   - `worker_exit_code`
   - `attempt_number`
   - `heartbeat_at`
   - `last_progress_at`
   - `current_operation`
   - `operation_started_at`
   - `browser_state`
   - `browser_restart_count`
   - `cancel_requested_at`
   - `cancel_requested_by`
   - `termination_reason`
2. 작업 프로세스가 살아 있는 동안 하트비트를 주기적으로 기록한다.
3. 기사·이슈·지역 완료 시에만 `last_progress_at`을 갱신한다.
4. 서버 시작·종료, 작업 시작·종료, Playwright 시작·종료 이벤트를 동일한 시간 기준으로 기록한다.
5. `run_web.py`의 stdout/stderr를 날짜별 파일로 보존한다.
6. 로그에는 비밀값·쿠키·인증 헤더를 남기지 않는다.

### 2단계: 장애 재현, 원인 판정, 계획 수정 — 완료

1. 다음 시나리오를 각각 분리해 실행한다.
   - 느린 기사 또는 응답 정지
   - 검사 페이지 강제 종료
   - Chromium 강제 종료
   - Playwright 드라이버 연결 종료
   - 작업 프로세스 종료
   - API 서버 정상 종료 및 비정상 종료
   - 화면 중단 버튼 요청
   - Windows 절전 후 복귀가 가능한 환경이면 별도 확인
2. 각 실행의 하트비트, 마지막 진행, PID, 종료 코드를 시간순으로 비교한다.
3. `docs/root-cause-report.md`를 작성한다.
4. 확정된 원인에 맞춰 이 문서의 3~8단계, 변경 파일, timeout, 재시작 정책을 수정한다.
5. 원인에 직접 대응하지 않는 복구 기능은 범위에서 제외하거나 후순위로 이동한다.

완료 결과는 `docs/root-cause-report.md`에 기록했다. 일반 HTTP 지연은 기존 호출 timeout으로 제한됐지만 기사 전체 deadline과 동시 취소 대기가 없었고, 브라우저 계층 종료 뒤 세션 복구가 없어 연쇄 실패하는 구조를 확인했다. worker·API 선행 종료와 Windows 절전은 2026-07-30 장애의 원인으로 확정되지 않았다.

### 3단계: 기사 상위 deadline과 중단 요청 처리 — 완료

1. 기사 한 건의 클릭·접속·판정·검증·정리를 `min(180, max(45, timeout_seconds * (retries + 1) + 15))`초의 상위 deadline으로 감싼다. 기본 설정은 105초다.
2. 기사 작업과 취소 토큰을 동시에 기다리고, 취소 토큰은 최대 0.5초 간격으로 확인한다.
3. 취소가 먼저 도착하면 기사 task를 취소하고 페이지·컨텍스트·브라우저 정리를 시작한다.
4. 개별 정리는 5초, 전체 정리는 10초를 넘기지 않는다.
5. 취소 요청 후 10초 안에 worker가 끝나지 않으면 `force_terminating`으로 전환하고 기록된 worker PID를 종료한다. 5초 뒤에도 같은 PID가 살아 있을 때만 최종 종료한다.
6. `cancel_requested` → `cancelling` → `force_terminating` → `cancelled` 상태를 저장한다.
7. 비정상 종료와 강제 취소에서는 마지막 `current_operation`, `operation_started_at`, `browser_state`를 지우지 않는다. 정상 완료에서만 초기화한다.
8. 완료된 체크포인트를 보존하고 가능한 경우 부분 Excel을 생성한다.
9. 취소 API를 반복 호출해도 현재 취소 단계를 성공 응답으로 반환하도록 멱등화한다.
10. 종료 대상은 기록된 해당 작업의 worker PID로 제한하며 전역 프로세스명 기반 종료는 금지한다.

완료 결과로 기사 작업과 취소 토큰을 경쟁 대기하도록 구성하고 기사 상위 deadline 및 5초/10초 정리 제한을 적용했다. 취소 상태 전이와 API 멱등성을 저장소·API·UI에 반영했으며, 10초 유예와 5초 최종 유예 뒤에도 실행 중일 때 DB에 기록된 동일 worker PID만 종료한다. 비정상·강제 종료 진단 상태와 기존 체크포인트·부분 Excel 흐름은 유지한다.

### 4단계: 체크포인트 완료 의미 수정

브라우저 복구보다 먼저 재개 기준을 확정한다.

1. 이슈 `started`, `completed`, `failed` 상태를 구분하고 이전 `issue` 레코드는 `started`로 해석한다.
2. 이슈 완료는 발견한 모든 출처가 처리 완료 또는 명시적 최종 실패 상태일 때만 기록한다.
3. 이슈 예외나 기사 누락이 있으면 지역 전체를 완료 처리하지 않는다.
4. 시작만 기록되고 끝나지 않은 이슈는 재개 대상으로 간주한다.
5. 손상된 마지막 JSONL 줄은 건너뛰고 이전 레코드 형식을 계속 읽는다.
6. 기사 행 중복 제거 규칙이 재개 전후 동일하게 유지되는지 확인한다.

### 5단계: 제한된 브라우저 세션 복구

1. 검사 페이지 `close`와 브라우저 `disconnected` 이벤트를 기록하고 `browser_state`를 `page_closed`, `disconnected`, `restarting`, `running`으로 구분한다.
2. 오류 문구만 사용하지 않고 `browser.is_connected()`와 수명주기 이벤트로 페이지 단독 종료와 브라우저·드라이버 세션 종료를 구분한다.
3. 페이지 단독 종료면 검사 page만 다시 만들고, 브라우저 또는 드라이버 연결 종료면 Playwright·브라우저·컨텍스트·BigKinds page를 재생성한다.
4. 현재 날짜와 지역으로 복귀하고 4단계 체크포인트상 미완료 이슈부터 다시 점검한다.
5. 복구는 기사당 1회, 작업당 2회로 제한한다. 상한을 넘으면 `partial_failed` 또는 `failed`로 끝낸다.
6. 사용자 취소 중에는 복구를 시작하지 않는다.
7. worker 자동 재시작, 서버 시작 시 자동 재개와 API 실행기 분리는 구현하지 않는다.

### 6단계: 3단계 진행 상태와 UI

1. 다음 상태를 저장하고 API로 반환한다.
   - 완료 날짜×지역 수와 전체 날짜×지역 수
   - 현재 지역 완료 이슈 수와 전체 이슈 수
   - 현재 이슈 처리 기사 수와 전체 기사 수
   - 현재 언론사와 기사 제목
2. 한 개의 진행 카드 안에 전체 일정·현재 지역 이슈·현재 이슈 기사 막대를 표시한다.
3. 분모를 모르는 동안 불확정 상태를 표시한다.
4. 이슈 전환 시 기사 진행을, 지역 전환 시 이슈·기사 진행을 명시적으로 초기화한다.
5. 하위 막대 초기화가 전체 진행률의 역행으로 오인되지 않도록 범위 라벨을 항상 표시한다.
6. `cancel_requested`, `cancelling`, `force_terminating`, `cancelled` 단계를 화면에 구분해 표시한다.

### 7단계: 복구·중단 후처리

1. 작업 프로세스 종료 후 상태가 계속 `running`으로 남지 않도록 한다.
2. 정상 완료에서만 현재 연산을 초기화하고 비정상 종료에서는 마지막 연산·브라우저 상태·종료 코드를 보존한다.
3. 부분 결과, 오류 메시지, 종료 사유 및 체크포인트 기반 수동 재개 가능 여부를 함께 저장한다.
4. 사용자 취소 작업은 재개 가능 대상으로 표시하지 않는다.
5. 서버 종료 시 worker가 끝나거나 3단계 강제 종료 폴백이 끝날 때까지 추적 목록에서 제거하지 않는다.
6. 서버 시작 시 이전 활성 작업을 자동 재실행하지 않고 취소 출처, 종료 사유와 체크포인트 상태로 `cancelled`, `partial_failed` 또는 `failed`를 판정한다.

### 8단계: 전체 검증

1. 단위 테스트와 로컬 브라우저 통합 테스트를 실행한다.
2. 느린 응답, 반환하지 않는 기사 task, 페이지·브라우저·드라이버 종료, worker 종료, API 종료와 UI 취소 장애 주입 테스트를 실행한다.
3. 실제 사이트에서 1일·1지역·이슈 1개로 확인한다.
4. 1일·복수 지역으로 확대한다.
5. 마지막으로 전체 17지역 장시간 실행을 수행한다.
6. 처리 기사 수, 체크포인트 행 수, SQLite 결과 수 및 Excel 결과 수를 대조한다.
7. Windows 절전 후 복귀는 안전하게 통제 가능한 별도 환경에서만 수행하고, 결과가 없으면 자동 재개 기능을 추가하지 않는다.

## 검증 명령

아래 명령은 구현 단계에서 실행한다. 현재 저장소의 `.venv`는 설치 당시 Python 경로를 찾지 못하므로 0단계에서 환경을 복구한 뒤 사용한다.

### 백엔드

```powershell
$testRunStamp = Get-Date -Format yyyyMMdd_HHmmss
python -m pytest -q tests -p no:cacheprovider --basetemp "work/pytest-$testRunStamp"
```

저장소 루트만 지정한 `python -m pytest -q`는 기존 `work/pytest-review-*` 디렉터리까지 수집해 소유권 오류가 발생하므로 사용하지 않는다.

관련 영역을 단계별로 검증할 때는 다음 명령을 사용한다.

```powershell
python -m pytest -q tests/test_job_manager.py
python -m pytest -q tests/test_audit_service.py
python -m pytest -q tests/test_api_jobs.py
python -m pytest -q tests/test_browser_link_flow.py
python -m pytest -q tests/test_checkpoint.py
python -m pytest -q tests/test_fault_injection.py
```

Playwright·Chromium 프로세스 실행이 샌드박스에서 `spawn EPERM`으로 차단되면 브라우저 테스트만 승인된 로컬 환경에서 다시 실행하고, 그 차이를 검증 보고에 기록한다.

## 위험과 롤백 방법

### 위험

1. **원인 오판**
   - 최초 오류가 아니라 후속 오류를 원인으로 판단할 수 있다.
   - 대응: 하트비트·서버 로그·프로세스 종료 코드의 시간순 상관관계가 확보되기 전 해결책을 확정하지 않는다.

2. **SQLite 스키마 호환성**
   - 신규 진행 및 관측 필드가 기존 DB와 충돌할 수 있다.
   - 대응: 추가형 마이그레이션만 사용하고 적용 전 DB 백업을 생성한다. 기존 열의 의미를 변경하지 않는다.

3. **체크포인트 호환성**
   - 새 이슈 상태가 기존 JSONL과 섞일 수 있다.
   - 대응: 기존 항목을 계속 읽을 수 있도록 하고 새 항목 유형은 무시 가능한 추가 레코드로 설계한다.

4. **강제 종료의 오대상 위험**
   - 사용자의 다른 Chrome 프로세스를 종료할 수 있다.
   - 대응: 작업이 생성하고 기록한 PID만 대상으로 하며 전역 프로세스명 기반 종료를 금지한다.

5. **자동 재시작 루프**
   - 같은 기사에서 계속 실패하면 무한 재시작할 수 있다.
   - 대응: 기사·브라우저·작업별 재시도 상한과 최종 `partial_failed` 전환을 둔다.

6. **중단 중 결과 손상**
   - 강제 종료가 체크포인트 한 줄을 쓰는 중 발생할 수 있다.
   - 대응: 한 줄 단위 append·flush를 유지하고, 로드 시 손상된 마지막 줄을 건너뛴다. 강제 종료 전 협력적 유예시간을 둔다.

7. **진행률 오해**
   - 이슈 또는 기사 막대가 다음 범위로 넘어가며 0으로 초기화되는 것을 전체 진행률 후퇴로 볼 수 있다.
   - 대응: 세 막대의 범위를 명확히 표시하고 전체 일정 막대는 별도로 단조 증가시킨다.

8. **실사이트 DOM·접근 제한 변화**
   - BigKinds 또는 언론사 DOM 변화, 접근 제한, CAPTCHA가 결과에 영향을 줄 수 있다.
   - 대응: 로컬 통합 테스트와 제한된 실사이트 테스트를 분리하고 CAPTCHA 우회 기능은 추가하지 않는다.

### 롤백 방법

롤백은 단계별로 독립 가능하도록 작은 변경 단위로 구현한다.

1. 관측 필드는 읽지 않아도 기존 실행이 가능하도록 선택 필드와 기본값으로 추가한다. 관측 기능 문제가 있으면 로그·하트비트 기록만 비활성화한다.
2. DB 마이그레이션 전 `work/web_jobs.sqlite3`와 `-wal`, `-shm` 파일을 서버가 정지된 상태에서 함께 백업한다. 롤백 시 새 코드를 되돌리고 백업 DB 세트를 복원한다.
3. 체크포인트 형식 변경 전 대상 JSONL을 별도 백업한다. 새 레코드 유형은 기존 로더가 무시할 수 있도록 설계한다.
4. 브라우저 복구, 자동 재시작 및 강제 종료는 각각 독립된 설정 또는 코드 경계로 구현해 개별 비활성화가 가능하게 한다.
5. UI 변경은 기존 전체 일정 진행 필드를 유지하므로, 문제가 생기면 이슈·기사 막대만 제거하고 기존 한 개 막대로 복귀할 수 있다.
6. 롤백 시 사용자 소유의 기존 결과·로그·체크포인트를 삭제하지 않는다.
7. Git을 이용한 롤백은 해당 단계의 변경 파일만 대상으로 하며, 관련 없는 사용자 변경을 되돌리지 않는다. `git reset --hard`는 사용하지 않는다.

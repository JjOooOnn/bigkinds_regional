# 결과·진행 화면 UI 개선 구현 계획

## 목표

다음 네 가지 화면 표시 문제를 프런트엔드에서 해결한다.

1. 진행 화면의 현재 이슈명이 화면 중앙을 기준으로 정렬되도록 한다.
2. 취소된 작업의 결과 제목을 `중단된 작업 결과예요`로 표시한다.
3. 완료·일부 실패·실패·중단 상태가 결과 제목에서 자연스러운 문장이 되도록 한다.
4. 오류 목록에서 `링크오류`와 `확인필요` 배지를 서로 다른 색으로 구분한다.

이번 변경은 표시 문구와 스타일에만 한정한다. 링크 판정 로직, 결과 데이터, SQLite 스키마, API 계약 및 Excel 생성은 변경하지 않는다.

## 현재 구조

### 진행 화면

`frontend/src/App.tsx`의 `ProgressScreen`이 작업 조회 응답의 `current_issue`를 `.current-issue-title` 요소로 표시한다. 프런트엔드는 활성 작업 동안 1.5초마다 `GET /api/jobs/{job_id}`와 로그 API를 조회한다.

현재 `frontend/src/styles.css`에는 `.status-hero { text-align: center; }`와 `.current-issue-title`의 최대 너비 및 좌우 자동 여백이 이미 있다. 그러나 제공된 화면에서는 이슈명이 왼쪽으로 치우쳐 보인다. 소스만으로 실제 브라우저의 계산된 스타일 또는 배포된 자산의 불일치를 확정할 수 없으므로, 직접 정렬 선언을 추가하고 실제 화면에서 확인한다.

### 결과 화면

`ResultsScreen`은 작업이 종료되면 `GET /api/jobs/{job_id}/results` 응답의 요약·오류 목록을 표시한다. 작업 상태 라벨은 `src/application/job_repository.py`의 `STATUS_LABELS`에서 생성되어 API로 전달된다.

현재 결과 제목은 완료 상태만 `점검이 완료됐어요`를 사용하고, 나머지 종료 상태에는 `${job.status_label} 작업 결과예요`를 사용한다. 따라서 `중단됨 작업 결과예요`뿐 아니라 `일부 실패 작업 결과예요`, `실패 작업 결과예요`도 결과 제목으로는 부자연스럽다.

오류 목록의 판정 배지는 모두 `.verdict-badge` 클래스를 사용한다. 오류 카드 안에서는 모든 배지에 같은 주황색 계열 스타일이 적용되어 `링크오류`와 `확인필요`를 색으로 구별할 수 없다.

## 채택한 방식과 이유

### 이슈명 정렬

`.current-issue-title`에 `text-align: center`를 직접 선언한다. 상위 요소의 상속에 의존하지 않으므로 CSS 우선순위 또는 컴포넌트 재사용으로 인한 정렬 회귀를 줄일 수 있다. `flex` 기반 중앙 배치는 긴 이슈명의 줄바꿈 처리에 불필요한 영향을 줄 수 있으므로 사용하지 않는다.

### 결과 제목

`status_label`은 상태 배지·실행 기록에 적합한 짧은 명사형 표기이므로 결과 제목에 재사용하지 않는다. `ResultsScreen` 안에 종료 상태별 제목 매핑을 두고, 다음 문구를 사용한다.

| 작업 상태 | 결과 제목 |
| --- | --- |
| `completed` | 점검이 완료됐어요 |
| `partial_failed` | 일부 점검 결과를 확인해 주세요 |
| `failed` | 점검을 완료하지 못했어요 |
| `cancelled` | 중단된 작업 결과예요 |

이 방식은 백엔드의 `status_label` 의미와 기존 실행 기록 표시를 바꾸지 않으므로 영향 범위가 가장 작다. 그 외 종료 상태가 발생할 경우에는 기존의 안전한 기본 문구를 유지한다.

### 오류 배지 색상

판정값을 의미 있는 배지 클래스에 매핑한다. `링크오류`는 기존 위험 색상 토큰(`--danger`) 계열, `확인필요`는 기존 경고 색상 계열을 사용한다. 두 색상 모두 현재 디자인 시스템에 존재하는 값이므로 새 색상 의존성을 추가하지 않는다.

요청에는 정확한 브랜드 색상 값이 제공되지 않았으므로, 실제 색상은 기존 위험·경고 계열의 대비와 가독성을 유지하는 범위에서 결정한다. 다른 판정 배지의 색상 변경은 이번 범위에 포함하지 않는다.

## 변경 대상 파일

- `frontend/src/App.tsx`
  - 상태별 결과 제목 매핑 추가
  - `링크오류`·`확인필요` 판정값에 따른 배지 클래스 추가
- `frontend/src/styles.css`
  - 현재 이슈명 직접 중앙 정렬
  - `링크오류` 및 `확인필요` 배지의 구분 스타일 추가
- `frontend/src/App.test.tsx`
  - 종료 상태별 제목과 배지 클래스 렌더링 회귀 테스트 추가

백엔드 파일과 API 타입은 변경하지 않는다. `frontend/dist`는 Git 추적 대상이 아니지만, 배포 전 빌드로 다시 생성해야 한다.

## 단계별 작업

### 1단계: 결과 제목을 상태별 문구로 분리

1. `ResultsScreen`에 상태별 제목 매핑을 추가한다.
2. 완료·일부 실패·실패·중단 상태에 각각 정해진 제목을 적용한다.
3. 상단 작은 상태 라벨과 실행 이력의 `status_label` 표기는 유지한다.

### 2단계: 이슈명 및 오류 배지 스타일 보강

1. `.current-issue-title`에 직접 중앙 정렬을 적용한다.
2. `링크오류`와 `확인필요`에 각각 의미 있는 추가 클래스를 부여한다.
3. 링크 오류는 위험 색상, 확인 필요는 경고 색상으로 표시한다.
4. 긴 이슈명과 좁은 화면에서 줄바꿈·가독성이 유지되는지 확인한다.

### 3단계: 자동·수동 검증 및 배포 산출물 생성

1. 프런트엔드 렌더링 테스트에 상태별 제목과 배지 구분을 추가한다.
2. 테스트·타입 검사·프로덕션 빌드를 실행한다.
3. 실제 제공 경로가 `frontend/dist`를 정적으로 제공하므로, 빌드 후 결과 화면을 데스크톱 및 모바일 폭에서 확인한다.

## 단계별 완료 기준

| 단계 | 완료 기준 |
| --- | --- |
| 1 | `completed`, `partial_failed`, `failed`, `cancelled`가 각각 지정된 결과 제목을 표시하고, 기존 상태 라벨 표기는 변하지 않는다. |
| 2 | 진행 화면의 긴 이슈명이 중앙 정렬되며, 동일 오류 목록에서 `링크오류`와 `확인필요` 배지가 명확히 다른 색으로 보인다. |
| 3 | 프런트엔드 테스트와 프로덕션 빌드가 성공하고, 데스크톱 및 800px 이하 화면에서 제목·이슈명·배지가 정상적으로 표시된다. |

## 검증 명령

프런트엔드 디렉터리에서 다음 명령을 실행한다. PowerShell 실행 정책 환경에서는 `npm.ps1` 대신 `npm.cmd`를 사용한다.

```powershell
cd frontend
npm.cmd test
npm.cmd run build
cd ..
```

수동 검증은 다음 순서로 수행한다.

1. 긴 `current_issue`를 가진 진행 중 작업에서 이슈명 정렬을 확인한다.
2. 완료·일부 실패·실패·중단 작업의 결과 제목을 각각 확인한다.
3. 동일 오류 목록에서 `링크오류`와 `확인필요` 배지의 색상과 텍스트 대비를 확인한다.
4. 데스크톱 폭과 800px 이하 폭에서 줄바꿈, 배지 위치, 필터 레이아웃을 확인한다.

`run_web.py`와 FastAPI는 기존 `frontend/dist`가 존재하면 자동 빌드를 수행하지 않는다. 따라서 배포 또는 로컬 정적 화면 확인 전에는 위 빌드 명령을 반드시 실행한다.

## 위험과 롤백 방법

### 위험

1. 실제 왼쪽 정렬의 원인이 현재 소스가 아닌 오래된 배포 자산 또는 외부 스타일일 수 있다.
   - 대응: 수정 후 실제 화면에서 이슈명 요소의 계산된 `text-align`과 로드된 CSS 자산을 확인한다.
2. 상태별 제목 문구가 제품 용어와 다를 수 있다.
   - 대응: 상태 라벨은 유지하고 결과 제목만 분리하므로, 문구 조정은 프런트엔드 한 곳에서 가능하게 한다.
3. 색상 대비가 특정 화면 또는 브라우저에서 충분하지 않을 수 있다.
   - 대응: 기존 위험·경고 색상을 사용하고, 밝은 배경과 텍스트 대비를 데스크톱·모바일에서 확인한다.
4. 배포 시 빌드 산출물을 갱신하지 않으면 소스 변경이 화면에 반영되지 않는다.
   - 대응: 배포 절차에 `npm.cmd run build`를 포함하고 생성된 `dist`로 화면을 다시 확인한다.

### 롤백 방법

1. 변경은 `frontend/src/App.tsx`, `frontend/src/styles.css`, `frontend/src/App.test.tsx`로 한정한다.
2. 문제가 발생하면 해당 UI 변경 커밋 또는 변경 블록만 되돌리고, 백엔드·SQLite·작업 결과 데이터는 건드리지 않는다.
3. `frontend/dist`는 빌드 산출물이므로, 롤백한 소스에서 다시 빌드해 정적 자산을 재생성한다.
4. 사용자 소유의 결과 파일, 체크포인트, SQLite 데이터 및 관련 없는 작업 트리 변경은 롤백 대상에 포함하지 않는다.
